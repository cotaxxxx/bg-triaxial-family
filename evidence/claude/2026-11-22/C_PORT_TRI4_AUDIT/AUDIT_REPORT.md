# Astra の C 版（tri4）の独立な照合と、速さについての試作｜報告

> 追記（2026-11-22）：指示書 v1.3 で、Reader の C への移植は Claude Code の担当になった。その作業は `evidence/claude-code/2026-11-22/C_PORT_TRI4/` に別に置く。この報告は、それより前に行った Astra の C 版の照合の記録である。

2026-11-22 ／ Claude Code ／ **DIAGNOSTIC_ONLY**（証拠ではない。採否は書かない）

## 0. 要点

1. **一致。** Astra の C 版は、私が別に作った箱 133 件、演算の素片の乱数試験 11,200 配列、Reader の自己試験 6 本、本番をなぞった包囲 36 回のすべてで、Python 版（Reader 0.6.0）と 1 ビットも違わなかった。例外の種類と文面、`enclose.last` の全項目も同じである。
2. **通らなかった分岐が 1 つある。** 「接触セルなしで、粗い格子のせいで二次の形をやめる」分岐は、133 件の中に 1 回も現れなかった。ただしこの分岐は NH = N のときには起こらない（§4）。本番は NH = N である。
3. **速さ。** 格子を使い回せる場合、Astra の C 版は Python 版の 1.4〜2.2 倍である。10 倍には届いていない。
4. **遅さの原因は算術ではない。** 内側のループを分岐のない形に書き直しても 5〜10% しか変わらなかった。1 演算ごとに全セルの配列を端から端まで読み書きすることが時間を決めている。
5. **試作（テープ版）。** Python の被積分関数を書き換えずに 1 回だけ記号的に走らせて演算の列を記録し、C の側でセルを 128 個ずつまとめて全演算を通す。同じ 133 件、自己試験 6 本、本番をなぞった包囲 36 回で Python 版と 1 ビットも違わず、格子を使い回せる場合の速さは Python 版の 3.6〜6.6 倍だった。
6. **本番では格子を作る時間が残る。** 本番の走らせ方をなぞると、包囲 36 回のうち 16 回で格子が作り直され、格子を作る時間（236 秒）がテープ版の包囲の時間（211 秒）を上回った（§8）。格子を作る部分は mpmath のままで、どの版でも速くならない。

以下、数値と、その読み方を分けて書く。

**通らなかった分岐。** `tri4.enclose` には「細かい格子では接触セルがないが、粗い格子（NH）のセルで D² の下端が 0 以下になるので、二次の形をやめる」という分岐がある（`order = 1`、`contact_cells = 0`、動く変数あり）。最初の 115 件に現れなかったので、追加の計画 1 でこの分岐をねらった箱を 18 件足したが、それでも現れなかった。不足としてそのまま記録する。

## 6. 遅さの原因についての読み

Astra の C 版は、区間の演算 1 つを 1 回の関数呼び出しにしている。呼び出しごとに、全セル分の配列（N = 256 なら 131,072 セル、下端と上端で約 2 MB）を新しく確保し、入力の配列を端から端まで読み、結果を端から端まで書く。被積分関数 1 回の評価は数千の演算からなるので、同じ大きさの配列を数千回、主記憶から出し入れする。1 要素あたりの算術は短いので、時間はメモリの読み書きで決まる。NumPy で書かれた Python 版も同じ形をしているので、C にしても 2 倍前後にとどまる。

これを確かめるために、Astra の `kernel.c` と同じ呼び出し口のまま、内側のループを分岐のない形（比較と選択だけ）に書き直した版を作った（`fast/kernel_fast.c`）。結果は 133 件すべてで一致し、速さは 5〜10% しか変わらなかった。算術を磨いても効かない、という観察である。原因の特定としては状況証拠であり、計測器で主記憶の通信量を直接測ったわけではない。

## 7. 試作：テープ版

### 7.1 考え方

計算を変えずに、計算の順番の「外側と内側」を入れ替える。

- いま：演算 1 → 全セル、演算 2 → 全セル、…
- テープ版：セル 1〜128 → 全演算、セル 129〜256 → 全演算、…

セルごとの計算は互いに独立なので、この入れ替えは各セルの演算の列を変えない。途中の値は 128 セル分の小さな作業場（数百 KB 以下）に置かれ、主記憶まで出ていかない。

### 7.2 作り

- `tape/_tape.py`：`tri4._make` と `tri3._make` が返す被積分関数を包む。初めての呼び出しのとき、**元の Python の関数をそのまま** 1 回、記号的な区間（`fiv.I` の子クラス）で走らせ、行われた区間演算（加、減、符号反転、乗、除、二乗、平方根、切り詰め、ほか被積分関数が直接使う 3 つの組み立て）を順に記録する。これがテープである。被積分関数、`dual.py`、`jet.py`、PQF の級数は書き換えない。演算の順序、Python の数の変換、ジェットの空の枠、ちょうど 0 の配列の扱いは、元のコードが行ったとおりに記録される。
- `tape/tape_kernel.c`：テープを 128 セルずつ再生する。各演算は `fiv.py` と同じ式（最近接丸めの演算のあと、下端は 1 つ下、上端は 1 つ上の浮動小数へ）で、積和演算は使わない（`-ffp-contract=off`）。最小・最大の NaN の扱いと符号付きの 0 も NumPy に合わせた。
- 配列全体にかかる条件（0 を含む区間での割り算、負の数の平方根）は、C の側で全セルについて調べ、`fiv.py` が例外を出すはずの最初の演算で、同じ例外を出す。
- 記録の途中で知らない操作や値による分岐に出会ったら、記録をやめ、その呼び出しは元の Python の関数で計算する（回数を数える）。
- 格子、`fsum`、角度の平均値の組み立て（`_mv_cells`）、一次と二次の形の組み立て、`enclose.last` は元の Python のままである。

行数は、`_tape.py` が 336 行、`tape_kernel.c` が 161 行である。

### 7.3 結果

§3 と §5 の表のとおり。133 件と自己試験 6 本、本番をなぞった 36 回で Python 版と一致し、元の Python の関数に戻った呼び出しは 0 回だった。テープの長さは、被積分関数の呼び出し 1 回につき 485〜2,819 演算（二次の形まで計算する包囲 1 回で 6 呼び出し、合計およそ 9 千演算）、作業場は区間 14〜144 個（128 セル分で最大約 300 KB）である。

### 7.4 限界

- 一致は、試した入力についての観察である。「記録した演算の列が、どの入力でも元の関数の演算の列と同じである」ことは証明していない。被積分関数が値によって道を変えない（配列全体の条件を除く）ことに頼っている。
- 1 台、1 つのコンパイラ、`-march=native`（sapphirerapids、256 ビットのベクトル）での結果である。別の CPU やコンパイラでは、一致をもう一度確かめる必要がある。
- Astra の指示書の試験 B（V61 の木の葉の一致）と、研究用 PC での確認は行っていない。
- 残る時間の大半は C の再生そのもの（N = 256 の E3 で 2.48 秒のうち 2.0 秒）で、次に削れるのは Python 側の `fsum` と組み立てだが、効果は 2 割以下である。
- これは速さについての提案の材料であり、Astra の C 版を置き換えるかどうかは私が決めることではない。
- 指示書 §7 の「独立の核」には当たらない。テープ版は Reader と同じ表現・同じ式をなぞるものであり、独立の核に流用してはならないという定めはテープ版にもそのまま当てはまる。

## 8. 本番の走らせ方をなぞった計測（追加の計画 2、`e289bf3`）

`replay_v63a.py` で、V63-A の 9 件（H33 が 8 件、W3 が 1 件）を、本番と同じ細分の規則・同じ呼び方（grade は規則どおり、NH = N、lazy あり、格子の置き場は 4 個まで）で、1 件あたり包囲 4 回まで進めた。3 つの版とも 3 本を同時に走らせた。

**一致。** 包囲 36 回と各件の終わりの記録 9 行、合わせて 45 行が、時間を除く全項目で 3 つの版で一致した（`results/compare_replay.json`、`results/rp_*.jsonl`）。

通った条件：N = 64 が 2 回、128 が 4 回、256 が 16 回、512 が 14 回。grade 1〜3 が各 4 回、grade 4 が 24 回。接触セルありが 4 回（W3 の 1 件）。lazy で二次の形を省いた回は 0 回（どの回も一次の形だけでは符号が決まらなかった）。9 件とも 4 回では終わらず、葉は 0 枚である。

**時間（秒、36 回の合計）。**

| | 格子を作る | 包囲そのもの | 合計 | Python 版との比（包囲／合計） |
|---|---:|---:|---:|---:|
| Python 版 | 237.9 | 1560.8 | 1798.7 | — |
| Astra の C 版 | 235.7 | 690.2 | 925.8 | ×2.26 ／ ×1.94 |
| テープ版 | 236.1 | 211.0 | 447.1 | ×7.40 ／ ×4.02 |

格子が新しく作られたのは 36 回のうち 16 回で、1 回あたり N = 256 で約 8〜10 秒、N = 512 で約 27〜29 秒だった。

読み方。

- 包囲そのものはテープ版で 7 倍になるが、格子を作る時間はどの版でも同じなので、合計では 4 倍にとどまる。テープ版では、格子を作る時間が包囲の時間を上回る。
- grade ≠ 0 の格子は、箱の q₃ の中心（の逆余弦を 1/256 に丸めた値）ごとに別のものである。q₃ を割るたびに作り直しになる。作り直しの割合が本番全体でどうなるかは、4 回までの入口しか見ていないので、ここからは分からない。これを見るための追加の計画 3（16 回まで）は固定したが、指示書 v1.3 で作業が切り替わったので、まだ走らせていない。
- 格子の時間の内訳（N = 128、grade 4、計装つき）は、セルごとの重みの数値積分（mpmath の `quad`）が約 7 割、N × 2N 個の積と外向きの丸めが約 2 割である。φ の方向（一様、2N セル）の部分は N だけで決まる。これを Reader の外から使い回す形にして試したところ、格子の時間は約 3 割減り、4 つの格子の全配列がビットまで同じだった（`grid_memo_probe.py`、`results/grid_memo_128.json`。計画の外の探りである）。θ の方向の数値積分を別の計算に置き換えれば大きく減るはずだが、それは値を変えうるので Reader の側の設計の話であり、試していない。

## 9. 計画からのずれと、私の誤り

- 最初の計画にあったのは、箱の照合（G1–G9）だけである。素片の乱数試験、自己試験、暖めた格子での計時、分岐なし版、テープ版は、最初の計画を固定したあとに足した。追加の計画 1 と 2 は、それぞれ走らせる前に固定した。追加の計画 3 は固定したが走らせていない。
- テープ版の最初の版は 133 件中 22 件で Python 版と違った（値の不一致と、形の合わない配列による例外）。原因は、記録のときに最初の呼び出しの「安全なセルの印」の配列をテープに抱え込み、あとの呼び出しでも使い回したことである。呼び出しごとの配列を使うように直し、133 件を全部やり直して 133 件一致を得た。照合の仕組みがこの誤りを捕まえた。直す前の結果ファイルは残していない。
- 環境の mpmath は 1.3.0 である。Reader の README が想定する版と違う場合は、その点も含めて「この環境での一致」と読む。
