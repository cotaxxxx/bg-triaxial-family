## 1. 作ったもの

| ファイル | 中身 |
|---|---|
| `src/tape_kernel.c`（252 行） | 記録された区間演算の列を、セル 128 個ずつ再生する C の核 |
| `src/_tape.py`（336 行） | 元の Python の被積分関数を 1 回だけ記号的に走らせて演算の列を記録し、C の核に渡す包み |

方式は計画 §1 に書いたとおりである。指示書と違う点を、ここにもう一度まとめる。

1. **式を人の手で C に書き写していない。** 元の被積分関数（`tri4._make`、`tri3._make` が返す関数）をそのまま 1 回走らせ、行われた区間演算を記録し、C がそれを同じ順に再生する。0 を足す・1 を掛けるの扱い、左からの順序、`2*a` や `int*I` の変換、`None` の成分は、元のコードが行ったとおりになる。Reader のファイルは、`__init__.py` の末尾に 2 行足す以外、書き換えていない。
2. **`_mv_cells` と `fsum` は Python のままである。** `fsum` は `math.fsum` そのものなので、和の一致は成り立つ。移す利点が小さいことは §5 の数字で示す。
3. **AVX2 を手で書いた。** `-O2` では自動のベクトル化が効かず、4 倍遅かった。使っているのは IEEE の加減乗除・平方根、`MINPD`／`MAXPD`、比較、整数の演算だけで、FMA の命令は書いていない。出来た `.so` を逆アセンブルして FMA の命令がないことをビルドのたびに確かめている。

ビルド（`results/build_c.log`）：

```
gcc (Ubuntu 13.3.0) 13.3.0
gcc -std=c11 -O2 -ffp-contract=off -fno-fast-math -mavx2 -fPIC -shared src/tape_kernel.c -lm -o geoenclosereader/libtape.so
FMA instructions: none
```

環境（`results/env.txt`）：x86-64、Intel Xeon 2.1 GHz（4 コア）、Linux、CPython 3.13.18、NumPy 2.5.3、mpmath 1.4.1。

## 6. 提案（実装していない。指示書 §1 の 1 による）

1. **格子の置き方。** grade ≠ 0 の格子は箱の q₃ の中心ごとに別のもので、q₃ を割るたびに作り直しになる。φ の方向（一様、2N セル）の部分は N だけで決まるので、そこを使い回すと、格子の時間は約 3 割減り、試した 4 つの格子では全配列がビットまで同じだった（先の照合の `grid_memo_probe.py`）。作った格子をファイルに置いてプロセスの間で使い回すことも、値を変えない。どちらも Reader の側の変更になるので、実装していない。
2. **核の並列化。** セルのブロックは互いに独立なので、C の核の中でブロックをスレッドに分けられる。`fsum` は Python の側で全配列に対して行うので、和の順序は変わらない。実装していない。
3. **AVX-512。** 研究用 PC の CPU は AVX-512 を持つ。8 セルずつの経路を足せる。足すなら、同じ試験 A〜E をその経路で流す必要がある。実装していない。
4. **抜き取り（指示書 §6）。** 包みには切り替え（`_tape.enabled`）があり、同じプロセスの中で、同じ箱を元の Python の関数で包み直せる。本計算での抜き取りは、これを使って書ける。本計算の計画の側で決めることなので、ここでは書いていない。

## 10. 監査の追補（Issue #1 への回答）

2026-11-22 追記。固定した試験 A〜E、その合否、試験の組は変えていない。`src/tape_kernel.c`、`src/_tape.py`、`src/build.sh` も変えていない（`PLAN.sha256` と照合済み）。足したのは、記録用の別ファイル 2 つ（`src/tape_log.py`、`src/run_with_log.py`）、その点検（`tests/test_tape_log.py`）、記録つきの流し直しの結果（`results/tape_log/`）である。

**最初に区別しておくこと。** 試験 A の 228 件でビットまで一致したことは、その 228 件とこの環境についての事実である。任意の入力で正しいことの証明ではない。以下で「根拠」と書くものは、ソースを読んだ結果と、仕組みによる検出と、試験の範囲の 3 種類で、どれであるかを分けて書く。

### 10.1 テープの再利用条件

テープは、次の 7 つの組（キー）が同じ呼び出しの間で使い回される（`_tape.py` の `_wrap`）。

| キーの要素 | 区別するもの | 例 |
|---|---|---|
| `module.__name__`、`name` | どの被積分関数の作り手か | `tri4._make`（内部用）と `tri3._make`（接触セルの印つき） |
| `kind` | 量の種類。被積分関数の中の `if kind == …` の分かれ道 | E3、T12、H33 |
| `safe_mask is not None` | 接触セルの印を使うかどうか（`tri3._make` だけ） | 接触セルのある箱とない箱 |
| `template` | 9 個の引数それぞれの構造。区間（I）か、双対数（D、勾配の成分の数）か、ジェット（J、変数の数、勾配のどの枠が `None` か、対のリスト、Hessian のどの枠が `None` か） | 動く変数が 5 個なら勾配は 5 成分、2 個なら 2 成分で、別のテープになる |
| `which` | 引数の葉のうち、どれとどれが同じ配列か | 0 の配列 `z` や 1 の配列 `one` が勾配のどの枠に入っているか。動く変数が {1, 4} か {0, 1} かは、ここで分かれる |
| `fullflag` | それぞれの入力が、格子の形の配列か、1 個の数（0 次元）か | 展開点での値（1 個の数）と、箱全体の区間を格子に広げたもの |

**キーに入っていないもの：** N、NH、grade、θ₀、セルの個数と格子の形、印（`safe_mask`）の値、入力の数値そのもの。

これらが演算の順序を変えないと考える根拠：

- （ソースを読んだ結果）被積分関数が通る関数は、`tri4._make`／`tri3._make` の `f`、`_common`、`_PQ_any`、`_PQ_d`、`tri.PQF`、`tri._tail`、`dual.py`、`jet.py` と、`fiv.I` のメソッドである。この中の分かれ道は、`kind` の比較、`isinstance`（I／D／J）、`is None`、`"P" in want` の類、添字の比較（`i == j`）だけで、どれもキーで決まる。N、grade、θ₀ は、入力の配列の値と形としてだけ入ってくる。テープは形を持たず、1 セル分の演算の列である。
- （仕組みによる検出）記録の間、区間の端点は数ではなく記号（`_TF`）である。端点に対してできるのは、`np.zeros_like` と、決まった形の `np.where` だけである。比較、真偽の判定、算術、配列への変換、ほかの NumPy の関数は `Unsupported` を出して記録をやめ、Python の関数に戻る。それ以外の触り方（属性の参照、`float()`）は Python の例外になって止まる。したがって、値を見て道を変えるコードがあれば、黙って片方の道だけを記録することはなく、戻るか止まるかになる。
- （試験の範囲）記録つきで流した V61 の木では、木 0 は 6 本のテープで 35 回の包囲・156 回の核の呼び出しを、木 1 は 6 本で 31 回・138 回をまかなった。箱と N が変わっても同じテープが使われ、葉のハッシュは Python 版と同じだった。試験 A でも、1 つのプロセスの中で N（16〜512）、grade（0〜4）、箱を変えながらテープを使い回している。
- （未検証）上の「検出」が、Python で書けるあらゆる書き方を漏れなく捕まえることは示していない。たとえば、モジュールの変数を実行の途中で書き換える、オブジェクトの `id` で道を変える、といったコードは捕まえられない。Reader 0.6.0（commit `1f84913`）にそういうコードがないことは読んで確かめたが、ほかの版については何も言えない。

**再記録と無効化：**

- テープはプロセスの中のメモリにだけあり、ファイルには残さない。新しいプロセスは、その木の Python のソースから毎回記録し直す。したがって、ソースを改訂したとき、別の環境に移したときに、古いテープが使われることはない。
- 1 つのプロセスの途中で Reader の関数や定数（`tri.NS` など）を書き換えた場合は、テープが古くなる。その場合は `_tape._cache.clear()` が要る。自動では検出しない。本計算でそういう書き換えをしないことが条件である。
- 記録に失敗したキーは「失敗」として覚えられ、以後その形の呼び出しは毎回 Python の関数に戻る（そのつど数える）。

### 10.3 適用外の入力と、Python の関数に戻ること

**いつ戻るか**（`_tape.py` の `Unsupported`。かっこの中が記録される理由の文面）：

- 格子の形の引数が 1 つもない、または形が 2 種類以上ある（argument shapes）。1 セルだけの格子はこれに当たる。
- 引数か戻り値が I／D／J でない（argument of type …、result of type …、concrete interval returned）。
- 端点に対する、決まった 2 つの形以外の NumPy の関数（numpy.…）、ufunc、配列への変換、真偽の判定、算術や比較。
- 被積分関数の中で配列の定数や配列の区間を作った（array constant inside the integrand、concrete array interval inside the integrand）、区間でも数でもないものを演算に使った（operand of type …）。
- 被積分関数の中の `hull`、`fsum`、`I.where`、形の合わない級数の尾（tail shapes）。
- `safe_mask` でない印を使った `where`（unknown mask）。
- `_tape.enabled = False` にしたとき（抜き取り用の切り替え）。

戻らずに**止まる**場合：記録の最中のそのほかの例外（`TypeError`、`AttributeError`）、核が 0 以外の状態を返したとき（`RuntimeError`）。

戻ったときは、その呼び出しの値は元の Python の関数が計算する。包囲の値も符号の判定も変わらず、失うのは速さだけである。数学的な符号の判定と、この性能上の退避は別のものである。

最後の行は、記録を付けて初めて分かったことである。**試験 C の 6 本のうち 3 本は、C の核を通っていない。** 3 本が FAILURES 0 であることは事実だが、C の核については何も確かめていない。試験 C の合否は計画どおり「合格」のままとし、この事実をここに書く。

固定した試験 B と C の最初の実行では、戻った回数を記録していなかった（ランナーと自己試験は書き換えずに使ったため）。上の「流し直し」は、同じランナー・同じ設定・同じ C 版の木を、記録を付けて流し直したものである。木 2 組の `leaf_sha256`・葉の数・評価回数は最初の実行と同じだった。

**本番での記録の仕方。** `src/tape_log.py` を足した。核と包みには手を入れず、`tri4.enclose` を素通しの包みで囲むだけである。

- 包囲 1 回の中で 1 度でも Python に戻ったら、その包囲について 1 行書く：量の種類、箱、N、NH、grade、lazy、核の呼び出し回数、戻った回数、理由ごとの回数、例外で終わったかどうか。
- 終了のときに 1 行書く：包囲の総数、例外の数、核の呼び出しの総数、記録したテープの数、戻った総数と理由ごとの回数、戻りのあった包囲の数、`tri4.enclose` の外で戻った回数、核のビルド（AVX2 かスカラーか）。
- ランナーを書き換えずに使う方法：`python3 src/run_with_log.py <記録ファイル> <C 版の木> <ランナー> <ランナーの引数…>`。ランナーの中に書くなら 2 行：`import tape_log; tape_log.install("out/tape_log_partN.jsonl")`。
- 点検（`tests/test_tape_log.py`、`results/tape_log_check.json`）：記録の側に `clip` を拒ませて、わざと全部を Python に戻した。3 つの包囲で 15 回戻り、3 行が箱・種類・N・NH・grade・理由つきで書かれ、包囲の両端と `enclose.last` は戻らない場合とビットまで同じだった。

本計算でこの記録を必ず付けること、戻りが出たときにどう扱うかは、本計算の計画（chat）で決めることである。
