## 0. 要点

- 試験 A の 228 件すべてで、包囲の両端と `enclose.last` の全項目が Python 版と 1 ビットまで同じだった。例外の種類と文面も同じだった。
- 試験 B の 2 組の木で、`leaf_sha256`・葉の数・評価回数が chat の記録と同じだった。
- 速さ（この機械）：格子が置き場にある状態の包囲 1 回は Python 版の 4.6〜6.9 倍。V61 の木 2 組は 3.0 倍。V60 の bench は 1.8 倍。差は、格子を作る時間（移していない）がどれだけ混ざるかで決まる。

## 1. 作ったもの

| ファイル | 中身 |
|---|---|
| `src/tape_kernel.c`（252 行） | 記録された区間演算の列を、セル 128 個ずつ再生する C の核 |
| `src/_tape.py`（336 行） | 元の Python の被積分関数を 1 回だけ記号的に走らせて演算の列を記録し、C の核に渡す包み |
| `src/build.sh` | 元の `GER2` を写し、核を作り、包みを入れる |

方式は計画 §1 に書いたとおりである。指示書と違う点を、ここにもう一度まとめる。

1. **式を人の手で C に書き写していない。** 元の被積分関数（`tri4._make`、`tri3._make` が返す関数）をそのまま 1 回走らせ、行われた区間演算を記録し、C がそれを同じ順に再生する。0 を足す・1 を掛けるの扱い、左からの順序、`2*a` や `int*I` の変換、`None` の成分は、元のコードが行ったとおりになる。Reader のファイルは、`__init__.py` の末尾に 2 行足す以外、書き換えていない。
2. **`_mv_cells` と `fsum` は Python のままである。** `fsum` は `math.fsum` そのものなので、和の一致は成り立つ。移す利点が小さいことは §5 の数字で示す。
3. **AVX2 を手で書いた。** `-O2` では自動のベクトル化が効かず、4 倍遅かった。使っているのは IEEE の加減乗除・平方根、`MINPD`／`MAXPD`、比較、整数の演算だけで、FMA の命令は書いていない。出来た `.so` を逆アセンブルして FMA の命令がないことをビルドのたびに確かめている。

ビルド（`results/build_c.log`）：

```
gcc (Ubuntu 13.3.0) 13.3.0
gcc -std=c11 -O2 -ffp-contract=off -fno-fast-math -mavx2 -fPIC -shared src/tape_kernel.c -lm -o geoenclosereader/libtape.so
FMA instructions: none
```

環境（`results/env.txt`）：x86-64、Intel Xeon 2.1 GHz（4 コア）、Linux、CPython 3.13.18、NumPy 2.5.3、mpmath 1.4.1。

## 5. C 版で残っている時間（`results/profile_c.json`）

格子がある状態の包囲 1 回を `cProfile` の下で流したときの内訳（秒）。

| 件 | 種類 | N | 合計 | C の核 | `fsum` | `_mv_cells` | そのほかの Python |
|---:|---|---:|---:|---:|---:|---:|---:|
| 2011 | H33 | 256 | 3.07 | 2.58 | 0.12 | 0.25 | 0.14 |
| 2020 | W3 | 256 | 1.18 | 0.98 | 0.04 | 0.03 | 0.13 |
| 2038 | C12 | 256 | 2.35 | 2.02 | 0.07 | 0.17 | 0.09 |

- 残りの 83〜86% は C の核そのものである。`fsum` と `_mv_cells` を合わせても 6〜12% で、C に移しても包囲は 1 割ほどしか速くならない。メモリは、移さなくても Python 版の 3 分の 1 になっている。この 2 つを移すかどうかは、この数字で判断できる。
- 格子を空から作る時間（N = 256 で 10〜12 秒、N = 512 で約 28 秒）は、C 版の包囲（2〜3 秒、N = 512 で 12〜14 秒）より長い。C 版にしたあとの全体の時間は、格子を何回作り直すかで決まる。

## 6. 提案（実装していない。指示書 §1 の 1 による）

1. **格子の置き方。** grade ≠ 0 の格子は箱の q₃ の中心ごとに別のもので、q₃ を割るたびに作り直しになる。φ の方向（一様、2N セル）の部分は N だけで決まるので、そこを使い回すと、格子の時間は約 3 割減り、試した 4 つの格子では全配列がビットまで同じだった（先の照合の `grid_memo_probe.py`）。作った格子をファイルに置いてプロセスの間で使い回すことも、値を変えない。どちらも Reader の側の変更になるので、実装していない。
2. **核の並列化。** セルのブロックは互いに独立なので、C の核の中でブロックをスレッドに分けられる。`fsum` は Python の側で全配列に対して行うので、和の順序は変わらない。実装していない。
3. **AVX-512。** 研究用 PC の CPU は AVX-512 を持つ。8 セルずつの経路を足せる。足すなら、同じ試験 A〜E をその経路で流す必要がある。実装していない。
4. **抜き取り（指示書 §6）。** 包みには切り替え（`_tape.enabled`）があり、同じプロセスの中で、同じ箱を元の Python の関数で包み直せる。本計算での抜き取りは、これを使って書ける。本計算の計画の側で決めることなので、ここでは書いていない。

## 7. 限界と、まだ確かめていないこと

- **1 台の機械、1 つのコンパイラ、1 つの Python と NumPy での結果である。** 研究用 PC（AMD Ryzen 9 9900X、CPython 3.11.16、NumPy 2.4.6、コンパイラの版は不明）では流していない。研究用 PC で使う前に、そこで `tests/run_all.sh` と `tests/evaluate.py` を流し、同じ条件を確かめる必要がある。手順：
  ```
  bash tests/run_all.sh <元の GER2> <v57 の場所> <V61 の束を解いた場所> <rep.json> <mpmath の場所（なければ空の場所）> <作業場所>
  python3 tests/evaluate.py <作業場所> tests <chat_checks/repro の場所> SUMMARY.json
  ```
- **一致は、試した入力についての観察である。** 「記録した演算の列が、どの入力でも元の関数の演算の列と同じである」ことは証明していない。これは、被積分関数が値によって道を変えないこと（配列全体にかかる条件を除く）に頼っている。記録の最中に値による分岐に出会えば Python の関数に戻る作りだが、その検出が完全であることも示していない。本計算では指示書 §6 の抜き取りが要る。
- 並列化はしていない。プロセスで分ける使い方（ランナーと同じ）だけを試した。
- 例外のうち、0 を含む区間での割り算と負の数の平方根は、228 件の中に現れなかった。そこで、計画の外の点検として `tests/test_errors.py` を足した。点 q を球面の上に置く（平方根の例外）、s か t を [−1, 1] にする（割り算の例外）の 51 通りを、C の核と元の Python の関数の両方で流した。例外になった 24 通り（平方根 18、割り算 6）は種類と文面が同じで、例外にならなかった 27 通りは全配列がビットまで同じだった。AVX2 版とスカラー版の両方で同じ結果である（`results/errors_c.json`、`results/errors_c_scalar.json`）。計画を固定したあとに足した点検なので、合否には数えない。
- 「INCONSISTENT」（一次と二次の包囲が交わらない）は、どの試験にも現れなかった。この判定は Python の側（`tri4.enclose`）にあり、移していない。

## 8. 計画からのずれ

- `tests/run_all.sh`、`tests/evaluate.py`、`tests/profile_c.py` は、計画を固定したあとに書いた。計画を実行し、結果を集めるだけのものである。`tests/test_errors.py` も固定のあとに足した（§7）。
- `tests/evaluate.py` の「時間の数字を除いた出力の比較」は、最初の版では `time 0.55` の形の行を除けておらず、自己試験 3 本で「違う」と出た。差は時間の行だけであることを確かめて、除く規則を直した。これは試験 C の合格の条件（FAILURES 0）には関わらない。
- 作業 1 の profile は、試験と同時に測った値（`results/profile.json`）のほかに、単独で測り直した値（`results/profile_alone.json`）を取り、`PROFILE.md` には後者を書いた。
- 計画 §4 の「暖めた格子での内訳」は、3 件（N = 256）を表にした。6 件分の値は `results/profile_c.json` にある。
