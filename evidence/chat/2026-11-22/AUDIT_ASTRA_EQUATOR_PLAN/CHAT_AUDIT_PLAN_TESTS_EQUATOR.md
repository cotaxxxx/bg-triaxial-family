## 2. 修正の要求

### R1（必須）E3 の 20 箱の母集団を、V63-A の葉に替える

**理由：** V61 の結果は、葉の箱そのものを記録していない（葉の列の hash だけ）。計画の §4 は「chat が同じ入力と順で木を再現し、元の葉の数で止めて hash を合わせる」としているが、選ばれた 20 個の ID は 10 組にまたがり、うち 4 組は葉の番号が 300 を超える（予算いっぱいの木）。chat の作業機で再現すると数十時間かかる。

V63-A の結果（`evidence/chat/2026-11-22/D_TRI_V63A_GRID/results/V63A_RESULT_20261122_0518.tar.gz`）には、**葉ごとの正確な有理数の箱、角度の格子 N、Reader の下端**が記録されている。E3 の目的（同じ箱で Reader の包囲と交わるか）には、こちらが正確で、すぐに使える。

**修正の内容：**
- 母集団：V63-A の 9 組のうち H₃₃・赤道の 8 組の葉、全 474 枚（縁の W₃ の 1 組は除く）。
- ID：`i,j,k,l,0,h`（タイル (i,j)、セル (k,l,0)、h はその組の `leaf_list` の中の順番、1 から）。
- 選び方：計画のとおり（ASCII の `20261126|` に ID を連結、SHA-256 の生のバイト列で昇順、同じなら ID の昇順、先頭 20 枚）。種は 20261126 のまま。
- Reader の包囲：chat が、V63-A と同じ設定（Reader 0.6.0、tri4.H33、記録された N、NH = N、grade はランナーと同じ式、lazy = True）で 20 箱を包み直し、[lo, hi] を渡す。**記録された下端と、包み直した下端が binary64 で一致することを、chat が確かめてから渡す**（一致しなければ E3_INPUT_MISSING）。
- 「別の候補への交換はしない」という計画の原則は守られている。母集団を、試験を流す前に、記録のある V63-A に固定し直すだけである。

### R2（必須、測定のみ）E4 で、方向ごとの寄与を記録する

**理由：** 設計（`DESIGN_EQUATOR.md`）は、帯の **a 方向の並進**を座標で止めるものである。設計自身が「長軸の効果が消えるのは帯の並進に限る」と書いている。一方、V62-B では、深い箱で s、t、q₁、q₂、q₃ の五つの寄与がそろって残っていた。E4 で完走しない組が出たとき、原因が a 方向か、ほかの四方向かを見分けられないと、次の判断ができない。

**修正の内容：** E4 の各評価（またはせめて深さごとの要約）に、パラメータの各方向（s、t、q₁、q₂、a）の寄与の幅と、角度の積分の幅（剰余を含む）を記録する。合否の条件にはしない。

## 3. 注意（修正は求めない）

- **計算の速さ：** 区間を MPFR の 128 ビットで計算する設計なので、binary64 より一回の評価が重くなる可能性がある。E4 は同じ予算での測定なので、これは結果に出る。v2.0 の試験 D（速さ）は別の計画で測る。
- **E2 の失敗の切り分け：** 参照値が包囲の外に出たときは、80 桁と 110 桁の両方の値と、包囲の両端を記録すること（計画の §3 の趣旨どおり）。

## 4. 次の手順

1. Astra が R1・R2 を入れた計画を commit する。
2. chat がその差分だけを確かめる。
3. chat が E3 の 20 箱と Reader の包囲を、封をした JSONL（Reader の数値の欄は別のファイルにし、Astra の端点の hash の登録後に開く）として登録する。
4. Astra が E1〜E3 を流す。E4 は研究 PC で、Dig の運用指示書に従う。
